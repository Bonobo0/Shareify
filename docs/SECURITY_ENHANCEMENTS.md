# Client-Side File Encryption/Decryption 보안 강화 제안

## 현재 구현 분석

### 기존 암호화 아키텍처
- **암호화 모드**: AES-CTR (AES-GCM과의 호환성 유지)
- **키 유도**: PBKDF2 (100,000 iterations, SHA-256)
- **Salt 길이**: 16바이트 (128비트)
- **Counter/IV**: AES-CTR: 16바이트, AES-GCM: 12바이트
- **스트리밍**: 5MB 청크 단위 암호화/복호화
- **인증 태그**: SHA-256 기반 커스텀 authTag (32바이트)

### 현재 구현된 보안 기능
- 클라이언트 측에서만 암호화/복호화 수행 (서버로 비밀번호 전송 안 함)
- 스트리밍 방식으로 메모리 효율성 확보
- 비밀번호 입력 시 눈 아이콘 토글로 가시성 제어
- 암호화된 파일 선택적 다운로드 (비밀번호별 다른 비밀번호 지원)

## 추가 보안 장치 제안

### 1. 암호화 키 강화

#### 1.1 Argon2 또는 scrypt 키 유도 알고리즘 도입
- **현재**: PBKDF2 (100,000 iterations)
- **제안**: Argon2id 또는 scrypt (메모리 집약적, GPU/ASIC 공격에 강함)
- **이유**: PBKDF2는 GPU 기반 병렬 공격에 취약. Argon2id는 메모리 집약적이라 공격자가 동시에 많은 해시를 계산하기 어려움

```javascript
// 제안: Argon2id 구현 예시 (Web Crypto 미지원 시 외부 라이브러리 필요)
// - time cost: 3
// - memory cost: 65,536 KB (64MB)
// - parallelism: 4
```

#### 1.2 키 유도 파라미터 동적 조정
- **제안**: 파일 크기/중요도에 따라 iterations 증가
- **구현**: 작은 파일은 100k, 큰 파일은 200k~500k iterations

#### 1.3 솔트 길이 확장
- **현재**: 16바이트 (128비트)
- **제안**: 32바이트 (256비트) - 향후 보안성 증대를 위해

---

### 2. 민감 데이터 메모리 보호

#### 2.1 Secure Memory 할당 (가능한 경우)
- **제안**: 비밀번호/키가 포함된 변수에 대해 메모리 즉시 지우기 기능 추가
- **방법**: 
  ```javascript
  // 복호화 후 즉시 메모리 정리
  function secureClear(array) {
    for (let i = 0; i < array.length; i++) {
      array[i] = 0;
    }
  }
  ```

#### 2.2 브라우저 메모리 스와핑 방지
- **제안**: `crypto.getRandomValues` 대신 `crypto.subtle` 사용 시 메모리 취약점 방지
- **주의**: 브라우저가 메모리를 디스크에 스와핑할 수 있음. 민감 정보는 가능한 한 짧은 시간 동안 유지

#### 2.3 전역 변수 노출 방지
- **문제**: `console.log`에 파일명/크기 로깅 (콘솔 로그에 민감 정보 남김)
- **제안**: 프로덕션 빌드에서 디버그 로그 제거 또는 마스킹
  ```javascript
  // 현재: console.log("암호화 시작:", file.name, "크기:", file.size);
  // 제안: console.log("[디버그] 암호화 시작"); // 파일명 제외
  ```

---

### 3. 비밀번호 입력 보안 강화

#### 3.1 비밀번호 강도 검증
- **제안**: 최소 길이, 복잡도 요구사항 추가
- **구현**:
  - 최소 12자 이상
  - 대소문자/숫자/특수문자 중 2종 이상 포함
  - 흔한 비밀번호 사전 체크 (HaveIBeenPwned API 활용)

#### 3.2 비밀번호 확인 (Double-entry)
- **제안**: 비밀번호 입력 후 확인용 필드 추가로 오타 방지
- **UI**: 암호화 시 두 필드 입력, 복호화 시 하나만 입력

#### 3.3 비밀번호 노출 방지 UX
- **제안**: 
  - 비밀번호 입력 후 자동으로 가리기
  - 브라우저 자동 완성 비활성화 (`autocomplete="off"`)
  - 클립보드 복사 방지 (붙여넣기 제한 옵션)

#### 3.4 비밀번호 히스토리 관리
- **제안**: 세션 내에서 이전에 사용한 비밀번호 기억하지 않기
- **방법**: 컴포넌트 언마운트 시 state 완전 초기화

---

### 4. 세션/상태 관리 보안

#### 4.1 암호화 상태 자동 만료
- **제안**: 암호화된 파일 미리보기/스트림에 TTL (Time To Live) 적용
- **구현**: 15분 이상 비활성 시 자동 로그아웃 또는 세션 종료

#### 4.2 다중 탭/창 세션 격리
- **제안**: `sessionStorage`를 활용해 탭 간 비밀번호 공유 방지
- **이유**: 동일 브라우저의 다른 탭에서 비밀번호가 유출될 수 있음

#### 4.3 페이지 이동/새로고침 방지
- **제안**: 암호화된 파일이 메모리에 있을 때 페이지 이탈 경고
- **예시**: React `beforeunload` 이벤트 활용

---

### 5. 네트워크/전송 보안

#### 5.1 다운로드 URL 추가 보호
- **현재**: presigned URL로 직접 다운로드
- **제안**:
  - 다운로드 URL에 서명 만료 시간 단축 (5~10분)
  - 다운로드 시 Referer 검증
  - 다운로드 토큰에 IP 제한

#### 5.2 복호화 스트리밍 중단 방지
- **제안**: 네트워크 끊김 시 암호화된 데이터 일부만 다운로드 방지
- **방법**: `Content-Range` 검증 또는 전체 다운로드 후 검증

#### 5.3 Content Security Policy (CSP) 강화
- **제안**: `script-src 'self'` 등으로 인라인 스크립트 실행 제한
- **이유**: XSS 공격으로 인한 비밀번호 탈취 방지

---

### 6. 파일 무결성 및 인증

#### 6.1 HMAC 기반 무결성 검증
- **현재**: SHA-256 authTag (단순 검증용)
- **제안**: HMAC-SHA256 도입 - 파일 변조 탐지 및 인증 강화
- **구현**: 파일 헤더에 HMAC 포함, 복호화 시 검증

#### 6.2 파일 버전/포맷 식별자
- **제안**: 암호화 포맷 버전 명시적 식별
- **예시**:
  ```
  [1바이트] 버전 (0x01, 0x02 등)
  [1바이트] 암호화 모드
  [16바이트] salt
  [16바이트] counter/IV
  [32바이트] HMAC-SHA256
  ```

#### 6.3 난수 시드 추적 방지
- **제안**: 암호화할 때마다 새로운 난수 사용 (이미 적용됨)
- **확인**: `generateSalt()`, `generateCounter()` 함수 검토 완료

---

### 7. 브라우저 호환성 및 폴백

#### 7.1 Web Crypto API 지원 여부 재확인
- **현재**: `window.crypto && window.crypto.subtle` 체크만 있음
- **제안**:  
  - 구형 브라우저 대비 AES-JS 폴백 선택권 제공
  - 구글 그랩톱 등에서 Web Crypto 미지원 시 경고 UI 표시

#### 7.2 WebAssembly 암호화 가속
- **제안**: 대용량 파일 AES 연산 시 WebAssembly 기반 암호화 엔진 사용
- **이유**: `crypto.subtle.encrypt`는 메인 스레드를 블로킹할 수 있음

---

### 8. 프론트엔드 보안 강화

#### 8.1 DevTools 탐지
- **제안**: 개발자 도구 열림 감지 시 경고 또는 세션 종료
- **방법**: 
  ```javascript
  // 타이머 기반 탐지
  setInterval(() => {
    if (window.devtools && window.devtools.open) {
      // 경고 또는 세션 종료 로직
    }
  }, 1000);
  ```

#### 8.2 화면 캡처 방지
- **제안**: 
  - `visibilitychange` 이벤트로 탭 전환 감지
  - 화면 캡처 시 복호화된 미리보기 차단
  - `mediaSession` API로 화면 녹화 방지

#### 8.3 디버깅 방지
- **제안**: `debugger` 연결 감지 (`setInterval`으로 함수 실행 시간 측정)
- **주의**: 완전한 방지는 불가능하지만 디버깅 난이도 상승

### 9. 로깅 및 모니터링

#### 9.1 보안 이벤트 로깅
- **제안**: 
  - 복호화 실패 시도 횟수 기록
  - 의심스러운 활동 감지 (여러 번의 실패, 특정 IP)
  - 클라이언트에서는 최소한의 로깅만 수행 (서버로 전송 안 함)

#### 9.2 오류 메시지 정보 최소화
- **현재**: `복호화에 실패했습니다. 비밀번호를 확인해주세요.` (일반적 메시지)
- **제안**: 정상화됨 - 현재 구현이 이상적

### 10. 향후 기술적 고려사항

#### 10.1 WebAuthn 통합
- **제안**: 생체 인증 또는 하드웨어 키를 통한 추가 인증
- **활용**: `navigator.credentials.get()`으로 비밀번호 대체 또는 보조

#### 10.2 Zero-Knowledge 아키텍처
- **제안**: 서버가 메타데이터조차 모를 수 있는 구조
- **확장**: 파일명/크기도 암호화하거나 난호화 (oblivious)

#### 10.3 분산 암호화
- **제안**: Shamir's Secret Sharing으로 비밀번호 분할 저장
- **사용 시나리오**: 글로벌 조직에서 다수의 신뢰된 당국자만이 복호화 가능

## 참고: OWASP 암호화 가이드

- **KEK (Key Encryption Key) 패턴**: 비밀번호 → KEK → 데이터 암호화
- **Nonce/IV 재사용 금지**: 현재 구현이 이미 준수
- **암호화 모드**: GCM > CTR > CBC (인증 기능 여부)
- **키 유도**: Argon2 > scrypt > PBKDF2

## 결론

현재 Shareify의 클라이언트 측 암호화 구현은 기본적인 보안을 충분히 제공하지만, 특히 **비밀번호 정책 강화**와 **메모리/로그 보안**이 우선적으로 개선될 수 있습니다. 특히 기업/기관용으로 사용한다면 추가적인 보안 인증 절차가 필요할 수 있습니다.
